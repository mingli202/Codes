# Review

The overall design is good but could be improved in some places.

The linked-list data structure is workable, but it makes simple operations (lookup, replacement, bounds checks) more indirect and increases the surface area for these invariants to leak. Moreover, the list are coupled with the game's logic. As such, if a future feature requires some type of list, a lot of methods would have to be reimplemented and there would be a lot of code duplication. Using generics to make a generic list would solve this problem. Also, the "Object" folder is a bad name, it should be either "Classes" or something more meaningful, and perhaps split it into subfolders since "Point" doesn't really belong in the same directory as subclasses of ACell.

A maintainability concern is that important game invariants are implicit and error handling is silent. If a level does not contain a player, GetPlayerPosition on an empty board returns (-1, -1) and MovePlayer simply returns the original board when the resulting position is out of bounds. That hides configuration errors and makes debugging difficult. Similarly, there is no explicit guarantee or validation that the board is rectangular, contains exactly one player, or that targets/contents are compatible. 

The highest risk is parsing robustness and invariants. EnsureStringsConform only compares the width of the first row and the overall row count, so ragged input (rows of unequal length) will pass validation and then fail at runtime when indexing into a short row. This is compounded by trimming: ParseBoard calls Trim() on the entire multiline string before splitting rows, which changes the grid if leading/trailing whitespace is present on the first or last row. The codebase even has tests that implicitly allow leading/trailing whitespace, which makes the validation rules less predictable and more dependent on subtle string preprocessing. A more robust design would normalize line endings, split into rows, and validate each row’s length against the first before parsing any characters, so that malformed input fails fast with a clear error.

Documentation and discoverability are adequate at the interface level but not at the system level. It takes reverse-engineering to learn the coordinate system (x is column, y is row, y increases downward, and origin is the top-left) and to understand the full symbol set for parsing. Those details are embedded in StringBoardParser and the examples rather than being summarized in one place. This increases the cost of adding features like box pushing or collision checks because the behavior and constraints are not expressed as a cohesive contract.

Testing is good overall, but it does not cover the highest-risk behaviors. The ExamplesSokoban.cs tests exercise parsing, drawing, and many small predicates; however, there are no tests for player movement and no tests for malformed rectangularity (e.g., uneven row lengths that pass the current width check).Valid-looking levels will parse but fail at runtime.
